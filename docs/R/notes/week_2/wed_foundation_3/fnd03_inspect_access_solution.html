Q4: the middle one — airquality["Temp"] keeps the data frame wrapping (the printed header gives it away). Rule of thumb to leave them with: $ for a column you’ll compute on; [rows, cols] for a rectangle; [[ ]] to dig one thing out of a container. Deeper indexing rules are drill material (M4), not lecture material.

Q5 expected order: actually run it: airquality ≈ 5.6 KB, mtcars ≈ 7.2 KB, iris ≈ 7.8 KB, so airquality < mtcars < iris. (mtcars is small in rows but its row names cost bytes — a fun 20-second aside if asked; otherwise just confirm the order from the output.)

Q6: about 16 copies (8 GB ≈ 8,000 MB; 8,000 / 500 = 16). The honest version: overhead means fewer in practice — the point is the order of magnitude reasoning, which is sub-outcome 1.12’s whole job.

# YT5
object.size(iris)
7256 bytes
object.size(iris$Sepal.Length)
1248 bytes

YT5: one column ≈ 1.2 KB of ≈ 7.8 KB — about 15%, less than 1/5. Why: the data frame carries overhead (names, row labels, the factor’s level table) beyond its raw numbers. Any answer noticing “less than 1/5, because the container itself costs something” is full credit.

5 · Exit question (8 min)

Model answer:

glimpse(mysterydata)      # structure: rows, columns, names, types
summary(mysterydata)      # ranges + WHERE the NAs are
head(mysterydata)         # what the values actually look like

mysterydata$score         # one column, as a vector

Any three of {glimpse/str, summary, head/tail, dim/nrow+ncol, names} with correct one-line justifications passes; the access line must be $score or [["score"]] (a vector) — ["score"] is a data frame, half credit with the explanation. The habit being graded: inspect before you compute — which is the E stage’s second half, forever.
